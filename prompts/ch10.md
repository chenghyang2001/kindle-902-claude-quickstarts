# ch10｜autonomous-coding：跨多個 session 的長時間自主寫程式 harness

## 這章在講什麼

- 長時間任務的關鍵不在讓一個 session 撐更久，而在讓每個 session 都能從檔案把狀態撿回來。這個 harness 每一輪都新建 client，代理對之前的 session 沒有任何記憶。
- 兩種角色分工：初始化代理只跑第 1 個 session，把規格展開成一份逐項可驗證的 `feature_list.json`（全部 `"passes": false`），並建立 `init.sh`、git 與專案骨架；寫程式代理從第 2 個 session 起每次只做一項。它們是同一支 harness 輪流送兩份提示詞，同一時間只有一個在跑。
- 三種交接媒介：`feature_list.json` 是唯一事實來源（只能把 `passes` 由 false 改 true，不可刪、改、合併、重排）；`claude-progress.txt` 是留給下一棒的筆記；git 提交是存檔點，下一棒用 `git log --oneline -20` 看歷史。
- 寫程式代理固定十步：了解現況 → 跑 `init.sh` → 先重測 1～2 項已通過的核心功能 → 挑一項未通過的 → 實作 → 從介面用瀏覽器自動化驗證 → 只改那一項的 `passes` → commit → 更新進度筆記 → 乾淨收尾。
- harness 外層迴圈很笨：判斷第一次與否只看 `feature_list.json` 存不存在；沒有「全部通過就停」的判斷；出錯就等 3 秒開新 session 重試。智慧在提示詞與檔案約定裡。
- 安全靠三層：作業系統層沙箱、檔案操作限制在專案資料夾、Bash 指令允許清單（`security.py` 的 PreToolUse hook，沒列的一律擋）。

## 作者做過的實驗／例子

- 內建規格 `prompts/app_spec.txt` 是「Claude.ai Clone」：React＋Vite 前端、Node.js＋Express 後端、SQLite。初始化代理要為它寫出至少 200 筆端到端測試，其中至少 25 筆要有 10 個以上步驟。
- README 的時間預期：第一個 session 要好幾分鐘、看起來像當掉；之後每個 session 約 5～15 分鐘；做完 200 項要很多個小時。想快一點就把功能數改成 20～50。
- `test_security.py` 列出該擋與該放的指令：`curl`、`wget`、`python app.py`、`touch`、`echo`、`rm -rf /`、`pkill python`、`chmod 777 file.sh`、`./setup.sh` 都該擋；`ls -la`、`npm install`、`git status`、`pkill node`、`chmod +x init.sh`、`./init.sh` 該放。
- 預設值：模型 `claude-sonnet-4-5-20250929`、每個 session `max_turns=1000`、session 之間等 3 秒、相對路徑的專案資料夾自動放到 `generations/` 底下。

## 教練解說要點

- 「兩個代理」不是兩個同時運作的程式，而是同一個迴圈裡 `is_first_run` 這個旗標決定送哪一份提示詞；兩者連系統提示都一樣。
- 清單不可刪改的規則只寫在提示詞裡，`agent.py` 與 `progress.py` 都沒有檢查。練習 2 會在自己的小 harness 加上這道檢查，體會「提示詞約定」與「程式強制」的差別。
- 每個 session 開場先重測已通過的功能，是因為上一棒可能弄壞東西而自己不知道；交接檔只說「做了什麼」，不保證「現在還是好的」。
- 小模擬裡模型是真的，但沒有瀏覽器、沒有 Claude Agent SDK、沒有沙箱：模型只產生文字，寫檔、驗證、commit 都由我們的小 harness 代做。要照實告訴學習者哪些部分被簡化。

## 演練

> 說明：演練類型：導讀＋小模擬（原始 harness 需要 Claude Agent SDK、API 金鑰、Puppeteer MCP，而且要跑好幾個小時；這裡實跑它不需要模型的安全模組與進度模組，再用 claude -p 模擬兩種角色的接力）。練習視窗工作目錄是 practice/。官方原始碼在 `~/workspace/claude-quickstarts/autonomous-coding`，只讀不改、不安裝它的依賴、不執行它的啟動指令；要看原始碼用 `PYTHONUTF8=1 python qs_source.py <相對路徑> [起始行 結束行]`。自己寫的程式只用 Python 標準庫（不可 pip 安裝任何套件），檔案放 practice/ch10/interactive/，用 `PYTHONUTF8=1 python ch10/interactive/xxx.py` 執行。需要真實模型時用 practice/llm_agent.py 的 ask／ask_json（走 claude -p，不設任何 API 金鑰、不 mock）。本章例外：練習 1 不呼叫模型，練習 2 呼叫 3 次（初始化 1 次＋寫程式 2 次），整章 3 次。

### 練習 1：實跑官方的安全 hook 與進度計數（離線）

**目的**：官方的 `security.py` 與 `progress.py` 只用標準庫，可以直接匯入執行。親手餵指令給 `bash_security_hook`，看允許清單怎麼判斷；再餵一份自己造的 `feature_list.json` 給 `count_passing_tests`，看 harness 眼中的「進度」是什麼。
**送給練習視窗的提示詞**：

```text
寫 ch10/interactive/offline_harness_parts.py（只用標準庫，不可 input()，30 秒內跑完，不呼叫模型）：
1. 開頭把 practice/ 加入 sys.path（Path(__file__).resolve().parents[2]），import qs_source，
   再把 qs_source.root() / "autonomous-coding" 加進 sys.path，然後
   from security import bash_security_hook, extract_commands, ALLOWED_COMMANDS
   from progress import count_passing_tests
2. A 段：印出 ALLOWED_COMMANDS 排序後的清單與個數。
3. B 段：對下列 14 個指令逐一呼叫
   asyncio.run(bash_security_hook({"tool_name": "Bash", "tool_input": {"command": cmd}}))，
   印表：指令｜extract_commands 的結果｜放行或擋下｜擋下的理由。
   ls -la、npm install && npm run build、git status || git init、cat a.txt | grep x、
   pkill node、pkill python、chmod +x init.sh、chmod 777 init.sh、./init.sh、./setup.sh、
   curl https://example.com、echo hello; rm -rf /、python app.py、echo "沒關的引號
   另外用 {"tool_name": "Write", ...} 呼叫一次，確認不是 Bash 的工具直接放行。
4. C 段：在 ch10/interactive/demo_project/ 寫一份 5 筆的 feature_list.json
   （欄位 category、description、steps、passes；其中 2 筆 passes 為 true），
   印出 count_passing_tests 的結果；再把檔案內容換成壞掉的 JSON、再把檔案刪掉，各呼叫一次並印結果。
5. D 段：用 qs_source.grep 在 autonomous-coding/agent.py 找出含 is_first_run、create_client、
   AUTO_CONTINUE_DELAY_SECONDS、max_iterations 的行，印成「行號｜程式碼」表，
   並在表後用三句話寫出外層迴圈的離開條件。
6. 把四段輸出存成 ch10/interactive/offline_harness_parts.md。
```

**觀察重點**：

- B 段 14 個指令裡，是不是只有 `ls -la`、`npm install && npm run build`、`git status || git init`、`cat a.txt | grep x`、`pkill node`、`chmod +x init.sh`、`./init.sh` 這 7 個放行？引號沒關的那個是不是因為「解析不了」被擋？
- C 段：壞掉的 JSON 與檔案不存在，是不是都回 `(0, 0)` 而不是丟例外？這代表 harness 分不出「還沒開始」與「清單壞了」。
- D 段：外層迴圈的離開條件是不是只有 `max_iterations`，找不到任何「全部通過就停」的判斷？

### 練習 2：用 claude -p 模擬兩種角色的接力

**目的**：自己寫一個幾十行的小 harness，重現本章四個重點：初始化與寫程式分工、每個 session 全新 context、狀態只靠 `feature_list.json`＋`claude-progress.txt`＋git 提交交接、清單只能改 `passes`。模型是真的；瀏覽器驗證改成程式的關鍵字檢查。
**送給練習視窗的提示詞**：

```text
寫 ch10/interactive/relay_sim.py（只用標準庫，不可 input()；共呼叫 claude -p 3 次，用 llm_agent.ask_json）：
情境：要完成的「應用程式」簡化成一份文件 manual.md（番茄鐘命令列工具的使用手冊）。
規格 app_spec.txt 由程式寫死：手冊要有「安裝」「開始計時」「暫停與繼續」三個小節，每節至少 60 個字，
且分別要出現關鍵字「pip」「start」「pause」。
1. 專案資料夾用 tempfile.mkdtemp(prefix="k902-relay-") 建在系統暫存區（避免在本 repo 裡產生巢狀 git），
   寫入 app_spec.txt。所有 git 指令用 subprocess 在該資料夾執行，並用 -c user.name=k902 -c user.email=k902@example.invalid。
2. session 1（初始化代理，第 1 次呼叫）：提示詞只給 app_spec.txt 的內容，要求輸出
   {"features":[{"category":"functional","description":"...","steps":["..."],"passes":false}, ...],
    "progress_note":"..."}，剛好 3 筆、依優先度排序、全部 passes 為 false。
   harness 把 features 寫成 feature_list.json、progress_note 寫成 claude-progress.txt、建立空的 manual.md，
   git init 並提交 "Initial setup: feature_list.json and project structure"。
3. session 2、3（寫程式代理，各呼叫 1 次）：每次都重新組提示詞，內容只有當下從磁碟讀到的
   app_spec.txt、feature_list.json、claude-progress.txt、git log --oneline -20 的輸出與 manual.md 目前內容，
   加上規則「這是全新的 context，你對之前的 session 沒有記憶；只做第一筆 passes 為 false 的功能；不可改動清單」。
   要求輸出 {"feature_index": 整數, "section_markdown": "## 小節標題\n內文", "progress_note": "..."}。
4. harness 收到後：把 section_markdown 附加到 manual.md → 用關鍵字與字數規則驗證該小節 →
   通過才把那一筆的 passes 改成 true（其他欄位與其他筆一律不動）→ git add -A 並 commit →
   用 progress_note 覆寫 claude-progress.txt（結尾加一行「目前 x/3 通過」）。
5. 防竄改檢查：每個 session 前後各存一份 feature_list.json，比對「筆數相同、每筆的 category／description／steps 完全相同、
   passes 只能由 false 變 true 且最多變 1 筆」，不符就印出差異並以非 0 結束碼離開。
6. 每個 session 結束印一列：session｜角色｜做了哪一筆｜驗證結果｜通過數/總數｜最新一筆 commit 訊息。
7. 最後把 feature_list.json、claude-progress.txt、manual.md、git log --oneline 的輸出複製到 ch10/interactive/relay/，
   並印出暫存專案資料夾的路徑與總呼叫次數（應為 3）。
```

**觀察重點**：

- session 3 的提示詞裡完全沒有 session 2 的對話，它是不是仍然知道要做第 2 筆？它是從哪個檔案知道的？
- 跑完是不是 2/3 通過、git log 有 3 筆提交（初始化 1 筆＋功能 2 筆）？剩下 1 筆要再跑一個 session 才會完成，這就是「接力」。
- 防竄改檢查有沒有被觸發？官方 harness 沒有這道檢查，只靠提示詞裡那句「刪改功能是災難」；兩種做法各有什麼風險？（模型輸出每次可能不同，照實記錄）
