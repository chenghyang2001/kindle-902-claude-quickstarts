# ch04｜browser-toolset：用 CDP 寫一個最小的瀏覽器工具組驅動程式

## 這章在講什麼

- 瀏覽器工具組（`browser_toolset_20260801`）是「在 `tools` 宣告一個項目，模型看到多個工具」：`navigate`、`read_page`、`left_click` 各自是獨立的工具呼叫。
- 分工很清楚：SDK 的抽象類別管工具 schema、網址檢查、拒絕沒實作的工具與工具迴圈；驅動程式只管「把一個動作在瀏覽器裡做出來」。
- 範例驅動程式 `CdpBrowser` 不用瀏覽器函式庫，直接用 WebSocket 送 CDP 的 JSON 指令，控制自己啟動的一個 Chromium 分頁，只實作五個工具。
- 模型看頁面靠的是文字：`read_page` 替標題、連結、按鈕、表單控制項編 `ref_N`，點擊時再用編號換回座標。這個範例沒有截圖。
- 安全邊界是 URL 政策加沙箱：政策只判斷模型要求的網址，管不到瀏覽器自己發的請求，所以 README 要求用拋棄式 profile 與對外連線管制。

## 作者做過的實驗／例子

- `run.py` 的預設任務是「Open example.com and tell me the page heading.」，預設放行 `example.com,iana.org`，預設模型 `claude-sonnet-5-5`，`max_tokens=1024`。
- `exercise.py` 不用模型：在 localhost 開一個只有標題、狀態文字、「Click me」按鈕與一個連結的小網頁，手寫 `tool_use` 送給 `browser.tool_result()`。
- README 記錄的結果：四個呼叫被回答（`navigate`、`read_page`、對 `ref_N` 的 `left_click`、`get_page_text`），兩個被拒絕（改用 `127.0.0.1` 的 `navigate`、超過 30 秒的 `wait`）。
- README 列了一長串「沒做的事」：截圖、捲動、打字、多分頁、對話框、請求攔截等，並說正式的驅動程式大多需要。

## 教練解說要點

- 先分清楚誰擋下了什麼：`127.0.0.1` 是 SDK 在驅動程式執行前用政策擋的；`wait` 31 秒是驅動程式自己擋的（註解說 SDK 沒有限制 `duration`）。
- `ref_N` 存在頁面的 `window` 上，換頁就失效；錯誤訊息直接叫模型「Call read_page again」，這是把錯誤寫給模型看的示範。
- 使用者不必先開瀏覽器：驅動程式用 `--remote-debugging-port=0` 自己啟動，再讀 `DevToolsActivePort` 取得端點。
- 練習 2 是真模型加假瀏覽器，而且轉接層的工具呼叫是用提示詞模擬的，不是 API 原生的 tool use，也不是真的工具組，要照實說。

## 演練

> 說明：演練類型：導讀＋小模擬（原始做法要 Chromium、新版 SDK 的 tool runner 與 API 金鑰，這裡不能實跑）。練習視窗工作目錄是 practice/。官方原始碼在 `~/workspace/claude-quickstarts/browser-toolset`，只讀不改、不安裝它的依賴、不執行它的啟動指令；要看原始碼用 `PYTHONUTF8=1 python qs_source.py <相對路徑> [起始行 結束行]`。自己寫的程式只用 Python 標準庫（不可 pip 安裝任何套件），檔案放 practice/ch04/interactive/，用 `PYTHONUTF8=1 python ch04/interactive/xxx.py` 執行。需要真實模型時用 practice/llm_agent.py 的 ask／ask_json，或 practice/claude_cli_client.py 的 Anthropic 相容介面（都走 claude -p，不設任何 API 金鑰、不 mock）；每個練習最多呼叫 2 次，整章最多 4 次。

### 練習 1：把驅動程式拆成「工具 → CDP 指令」對照表

**目的**：不執行官方程式，只靠讀原始碼看出五個工具各用了哪些 CDP 指令，以及哪些事其實是 SDK 做的。
**送給練習視窗的提示詞**：

```text
寫 ch04/interactive/driver_map.py（只用標準庫，不可 input()，30 秒內跑完，不呼叫模型，不可 import 官方模組）：
1. 用 qs_source 的 read_text 讀 browser-toolset/python/cdp_browser.py，當純文字分析。
2. 找出每個 @override 的方法名與行號；對每個方法的內文，抓 self._send("X.y") 的指令名，以及它用到的 JS 常數（READ_PAGE、RESOLVE_REF、PAGE_INFO、PAGE_TEXT）。
3. 印表一：方法｜行號｜直接送的 CDP 指令｜用到的 JS 常數。
4. 印表二：全檔不重複的 "Domain.method" 字串與出現行號，標明哪一個是事件不是指令。
5. 印表三：COMMAND_TIMEOUT_S、TAB_ID 的值，以及 _launch 裡所有 "--" 開頭的啟動參數。
6. 用 grep 數 browser_toolset_20260801 在 README.md 與三個 .py 各出現幾次。
7. 三張表存成 ch04/interactive/driver_map.md。
```

**觀察重點**：

- `@override` 是否正好 7 個（五個工具加 `close` 與 `_browser_state`）？
- 不重複的 `Domain.method` 是否 10 個，其中 `Page.lifecycleEvent` 是事件、其餘 9 個是指令？`read_page` 與 `get_page_text` 是否都沒有直接呼叫 `_send`？
- 型別字串是否只在 README 出現 1 次、三個 .py 都是 0 次？這說明字串是誰送出去的？

### 練習 2：真模型＋假瀏覽器，跑一個兩回合的工具迴圈

**目的**：用文字狀態的假瀏覽器重現 `exercise.py` 的小網頁，讓真模型自己決定點哪個 `ref_N`，並體會政策拒絕與呼叫上限。
**送給練習視窗的提示詞**：

```text
寫 ch04/interactive/fake_browser_loop.py（只用標準庫，不可 input()）。瀏覽器是假的，模型是真的：
1. 假環境 FakeBrowser：只有一頁 http://localhost:8000/，狀態是 clicked=False。方法比照官方：
   navigate(url)：網址不是以 http://localhost:8000 開頭就丟錯 "blocked: <url> is outside this exercise's page"。
   read_page()：回傳三行 - heading "Exercise page" [ref_1]、- button "Click me" [ref_2]、- link "About this page" [ref_3]。
   left_click(ref)：ref_2 把 clicked 設成 True；不認得的 ref 丟錯 "Unknown or stale ref"。
   get_page_text()：依 clicked 回傳 "The button has not been clicked." 或 "The button was clicked."。
2. 程式先自己做三步並記錄（不經模型）：navigate 首頁、read_page、navigate 到 http://127.0.0.1:8000/（預期被拒絕）。
3. 把 left_click、get_page_text、read_page 定義成自訂工具（name、description、input_schema），用 claude_cli_client.Anthropic().messages.create 跑迴圈，最多 2 次呼叫。第一則訊息附上第 2 步的 read_page 結果，任務是「按下 Click me，再確認頁面文字有沒有改變」。
4. 每回合把 tool_use 交給 FakeBrowser 執行，結果（錯誤時 is_error=True）包成 tool_result 放回 messages。
5. 印出並存成 ch04/interactive/loop_log.md：步驟｜誰發起（程式或模型）｜工具｜輸入｜結果｜is_error；最後一行寫 clicked 的值、calls_made()，並註明「假瀏覽器＋提示詞模擬的工具呼叫」。
```

**觀察重點**：

- 模型第 1 次呼叫是否就選 `left_click` 且 ref 是 `ref_2`，沒有人告訴它編號對應哪個按鈕？
- 第 2 次呼叫是 `get_page_text` 還是直接宣稱完成？最後 `clicked` 是否為 True？（每次模型輸出可能不同，照實記錄）
- `127.0.0.1` 那一步是否以 `blocked:` 開頭且 is_error 為 True？這一步在官方做法裡是誰擋的？
