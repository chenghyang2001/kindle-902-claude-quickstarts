# ch06｜computer-toolset：用 VNC 寫一個最小的電腦操作工具組驅動程式

## 這章在講什麼

- 電腦操作工具組（`computer_toolset_20260801`）和第 4 章同一個模式：`tools` 宣告一個項目，模型把 `screenshot`、`left_click`、`type` 等當成各自獨立的工具來呼叫。
- 核心迴圈是「截圖 → 模型決定動作 → 驅動程式執行 → 再截圖」。模型只看得到圖，座標是它自己從圖上估的。
- 範例驅動程式 `VncComputer` 不用 VNC 函式庫，直接用 socket 加 `struct.pack` 講 RFB 協定，實作十個工具；其餘七個由 SDK 回報停用並拒絕。
- 動作其實很少：一個 PointerEvent、一個 KeyEvent。點擊、雙擊、三擊、捲動共用 `_click`，只差按鍵遮罩與次數。
- 人工把關放在工具組的 `confirm` 選項：`run.py` 對截圖以外的每個動作都先問 y/N，因為聚焦的終端機會執行模型打的任何字。

## 作者做過的實驗／例子

- `run.py` 的預設任務是「Open a terminal, run date, and tell me today's date and time zone.」，預設模型 `claude-sonnet-5-5`，`max_tokens=4096`，連 `127.0.0.1:5900`。
- README 給的桌面是 `Xvnc :1 -geometry 1280x800 -depth 24 -SecurityTypes None -localhost -rfbport 5900` 加一個 `xterm`。
- `exercise.py` 不用模型：六個呼叫被回答（`screenshot`、螢幕中心的 `left_click`、`type`、`key`、`wait`、第二張 `screenshot`），兩個被拒絕（超出螢幕一個像素的 `left_click`、沒實作的 `zoom`）。
- README 記錄的數字：螢幕上限 1920×1200；Raw 編碼下 1280×800 一張截圖約 4 MB；伺服器不回應時截圖等 10 秒後失敗。

## 教練解說要點

- 座標出界是「拒絕」不是「夾回邊界」，程式的說法是要讓模型看到自己的錯；這和第 4 章過期的 `ref_N` 是同一種設計。
- VNC 沒有「動作做完」的訊號，所以截圖前固定睡 0.5 秒，截圖仍可能是舊畫面；也沒辦法問游標在哪，驅動程式只好自己記 `_cursor`。
- 兩個被拒絕的呼叫是不同層擋的：出界座標是驅動程式丟 `ToolError`，`zoom` 是 SDK 因為沒實作而拒絕。
- 練習 2 的桌面是假的：截圖用文字描述代替 PNG，`date` 的輸出是寫死的字串，工具呼叫也是轉接層用提示詞模擬的，要照實說。

## 演練

> 說明：演練類型：導讀＋小模擬（原始做法要 VNC 桌面、新版 SDK 的 tool runner 與 API 金鑰，這裡不能實跑）。練習視窗工作目錄是 practice/。官方原始碼在 `~/workspace/claude-quickstarts/computer-toolset`，只讀不改、不安裝它的依賴、不執行它的啟動指令；要看原始碼用 `PYTHONUTF8=1 python qs_source.py <相對路徑> [起始行 結束行]`。自己寫的程式只用 Python 標準庫（不可 pip 安裝任何套件），檔案放 practice/ch06/interactive/，用 `PYTHONUTF8=1 python ch06/interactive/xxx.py` 執行。需要真實模型時用 practice/llm_agent.py 的 ask／ask_json，或 practice/claude_cli_client.py 的 Anthropic 相容介面（都走 claude -p，不設任何 API 金鑰、不 mock）；每個練習最多呼叫 2 次，整章最多 4 次。

### 練習 1：把驅動程式拆成「工具 → RFB 訊息」對照表

**目的**：不執行官方程式，只靠讀原始碼看出十個工具最後都落在哪幾種 RFB 訊息，並驗算 README 的截圖大小。
**送給練習視窗的提示詞**：

```text
寫 ch06/interactive/rfb_map.py（只用標準庫，不可 input()，30 秒內跑完，不呼叫模型，不可 import 官方模組）：
1. 用 qs_source 的 read_text 讀 computer-toolset/python/vnc_computer.py，當純文字分析。
2. 找出每個 @override 的方法名與行號，以及它的內文呼叫了哪個內部函式（_click、_move、_keys）或直接 sendall。
3. 找出全檔每個 struct.pack 的行號、格式字串、第一個數值參數（訊息型別），用 struct.calcsize 算出位元組數，並依型別 0、2、3、4、5 標上 SetPixelFormat、SetEncodings、FramebufferUpdateRequest、KeyEvent、PointerEvent。
4. 印表一：工具｜行號｜走哪個內部函式｜最後變成哪種 RFB 訊息。
5. 印表二：訊息型別｜名稱｜格式字串｜位元組數｜行號。
6. 印常數：MAX_WIDTH、MAX_HEIGHT、LEFT、RIGHT、WHEEL；KEYSYMS 裡引號寫出的鍵名個數，再加 f1～f12 的總數。
7. 驗算：1280*800*4 是幾個位元組、幾 MB。
8. 全部存成 ch06/interactive/rfb_map.md。
```

**觀察重點**：

- `@override` 是否 11 個（十個工具加 `close`）？`struct.pack` 是否 5 處、剛好對應五種訊息型別？
- PointerEvent 是否 6 個位元組、KeyEvent 8 個位元組？`KEYSYMS` 是否 23 個鍵名加 12 個功能鍵共 35 個？
- 驗算結果是否 4,096,000 位元組，對得上 README 的「about 4 MB」？

### 練習 2：真模型＋假桌面，跑一個兩回合的截圖→動作迴圈

**目的**：用文字狀態的假桌面重現 README 的 `date` 任務，讓真模型決定要打什麼字，並加上自動記錄的確認關卡。
**送給練習視窗的提示詞**：

```text
寫 ch06/interactive/fake_desktop_loop.py（只用標準庫，不可 input()）。桌面是假的，模型是真的：
1. 假環境 FakeDesktop：螢幕 1280x800，有一個終端機視窗佔 (100,100)～(900,600)；狀態有 focused=False、buffer=""、lines=[]。
   screenshot()：不產生圖，回傳文字，例如「螢幕 1280x800；終端機視窗 (100,100)-(900,600)，focused=…；畫面文字：…；輸入列：$ …」。
   left_click(coordinate)：座標超出螢幕就丟錯 "(x, y) is outside the 1280x800 screen"；落在視窗內則 focused=True。
   type(text)：沒聚焦就忽略；逐字加進 buffer，遇到 "\n" 視同按 Return。
   key(text)：只認 Return，其他丟錯 "unknown key"。
   Return 的效果：buffer 是 date 時在 lines 加一行寫死的假輸出 "Thu Jan  1 00:00:00 UTC 2030"，否則加 "command not found"，然後清空 buffer。
2. 確認關卡 confirm(name, input)：screenshot 直接放行；其他印出 "Allow <name> <json>? -> y（自動放行）" 並記錄。
3. 程式先自己做三步並記錄：screenshot、left_click [640,400]、left_click [1280,800]（預期被拒絕）。
4. 把 screenshot、left_click、type、key 定義成自訂工具，用 claude_cli_client.Anthropic().messages.create 跑迴圈，最多 2 次呼叫。第一則訊息附上聚焦後的 screenshot 文字，任務是「在終端機執行 date」。
5. 每回合執行 tool_use 並把結果包成 tool_result 放回 messages。
6. 印出並存成 ch06/interactive/loop_log.md：步驟｜誰發起｜工具｜輸入｜有沒有經過確認｜結果｜is_error；最後寫 lines 內容、calls_made()，並註明「假桌面、假 date 輸出、提示詞模擬的工具呼叫」。
```

**觀察重點**：

- 模型是一次送 `type` 的 "date\n"，還是先 `type` "date" 再 `key` "Return"？兩種是否都讓 `lines` 出現假日期？（每次輸出可能不同，照實記錄）
- 確認紀錄的筆數是否等於截圖以外的動作數？
- `[1280,800]` 是否被拒絕且訊息含 `outside`？為什麼右下角合法的最大座標是 `[1279,799]`？
