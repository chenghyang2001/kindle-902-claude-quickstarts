# ch09｜managed-agents：把代理交給 Anthropic 代管的 12 個範例

## 這章在講什麼

- Claude Managed Agents 把代理迴圈搬到伺服器端：Anthropic 替你跑 session、沙箱與工具，你的程式只建立資源、送訊息、讀事件串流、回答自訂工具。
- 資源寫成檔案再用 `ant apply` 建立：agent、environment（沙箱與網路白名單）、vault（憑證）、memory store（跨 session 的檔案式記憶）、deployment（cron 排程），ID 記在 `claude-lock.json`。
- 跨次執行的連續性有兩種來源：memory store（`daily-brief` 的書籤與帳本、`knowledge-wiki` 的 wiki），以及 session 的 `metadata` 加事件紀錄（`sentry-autofix` 主機重啟後靠重播接續）。
- 無人值守的代理要安全地失敗：讀不到的來源要明說、確認成功後才記帳、有花費上限（到上限是暫停）。
- 安全靠外圍：沙箱拿不到真正的憑證、網路預設全擋、關鍵決定留在主機。

## 作者做過的實驗／例子

- `daily-brief` README 的實測：忙碌的一天（約 140 則訊息與 25 個 PR）一次約 1.50 美元（Claude Opus 5）或 1.00 美元（Claude Sonnet 5）；排程是工作日 07:32，每次上限 5 美元。
- `sentry-autofix` 附的 `demo-app/` 是有真 bug 的結帳服務：沒有折扣碼的購物車回 500。每個 session 上限預設 10 美元，同時最多 3 個修復。
- `knowledge-wiki` 用公開的 SEC 文件：`core` 層 8 份、2.8 MB 文字，錄製的那次建置花 23 分鐘、約 16 美元。

## 教練解說要點

- 先看「狀態存在哪裡」：聊天類靠 session 本身，webhook 橋接類靠 session `metadata`，排程類才需要 memory store。
- 書籤取代「最近 24 小時」，晚跑或漏跑不掉資料；往前多讀十分鐘必然重疊，所以要有帳本擋重複，兩者是一組。
- 「讀不到」和「沒東西」必須分開：失敗的來源書籤不能動，簡報要寫明讀不到。
- 練習 2 只重現記憶與記帳的順序，沙箱、vault、cron 都是假的，要說清楚。

## 演練

> 說明：演練類型：導讀＋小模擬（原專案需要 Claude Managed Agents 雲端服務、`ant` CLI 與 Slack／GitHub／Sentry 帳號，這裡不能實跑）。練習視窗工作目錄是 practice/。官方原始碼在 `~/workspace/claude-quickstarts/managed-agents`，只讀不改、不安裝它的依賴、不執行它的啟動指令；要看原始碼用 `PYTHONUTF8=1 python qs_source.py <相對路徑> [起始行 結束行]`。自己寫的程式只用 Python 標準庫（不可 pip 安裝任何套件），檔案放 practice/ch09/interactive/，用 `PYTHONUTF8=1 python ch09/interactive/xxx.py` 執行。需要真實模型時用 practice/llm_agent.py 的 ask／ask_json，或 practice/claude_cli_client.py 的 Anthropic 相容介面（都走 claude -p，不設任何 API 金鑰、不 mock）；每個練習最多呼叫 2 次，整章最多 4 次。

### 練習 1：12 個子專案總表與 daily-brief 設定檔拆解（離線）

**目的**：從原始碼整理每個子專案的代理設定、觸發方式與狀態位置，並看懂一份 agent 與 deployment 設定檔。
**送給練習視窗的提示詞**：

```text
寫 ch09/interactive/survey.py（只用標準庫，不可 input()，30 秒內跑完，不呼叫模型）：
1. 用 qs_source 的 root() 找到 managed-agents/，列出所有子資料夾。
2. 對每個子專案：
   a. 找 agents/ 底下（含更深層）的 .md、.yaml 檔，逐行字串比對（不用 YAML 套件）抓 model 的值；沒有就記「無設定檔」。
   b. 在 README.md、CLAUDE.md 與上述設定檔裡數關鍵字次數：cron、webhook、memory_store 或 memory store、metadata、multiagent、budget。
   c. 推測觸發方式：設定檔有 cron→排程；否則 webhook≥3 次→webhook；否則→聊天或手動。
3. 印表並存成 ch09/interactive/survey.csv：子專案｜設定檔數｜模型｜觸發方式（推測）｜memory｜metadata｜multiagent｜budget；表尾註明觸發方式是關鍵字推測。
4. 拆解 managed-agents/daily-brief/agents/daily-brief/ 的 agent.md 與 deployment.md 的 frontmatter（兩個 --- 之間）：印出 model、mcp_servers 的 name 與 url、被停用的工具、MCP 工具組的 permission_policy、cron expression、timezone、兩個 resources 的 path 與 access、budget amount（換算成美元）。
5. 數出 agent.md 本文有幾個編號步驟，印出每步前 60 個字元。
```

**觀察重點**：

- 是否剛好 12 個子專案？哪些沒有 agents/ 設定檔（預期 `mcp-server-typescript`、`knowledge-wiki`、`chat-sdk`）？
- `sentry` 的 cron 寫在 `deploy.py`，是否被誤判成不是排程？
- `daily-brief` 是否為 `claude-sonnet-5-5`、cron `32 7 * * 1-5`、預算 `"500"` 等於 5.00 美元、`preferences` 唯讀而 `state` 讀寫、本文 8 個步驟？

### 練習 2：模擬 daily-brief 的跨次記憶（真模型＋假環境）

**目的**：用本機檔案當假的 memory store 連跑兩「天」，驗證第二天只處理新項目、不重複、讀不到的來源不移動書籤。
**送給練習視窗的提示詞**：

```text
寫 ch09/interactive/brief_sim.py（只用標準庫，不可 input()）。模型是真的；Slack、GitHub、memory store、排程、貼文全部是假的，用本機檔案與 Python 函式代替，報告裡要寫明。
1. 假的 state store：資料夾 ch09/interactive/state/（每次執行先清空），放 bookmarks.json、ledger.md、runs/dayN.md。假的 preferences 是程式裡的唯讀字串：最多 5 行、不提已關閉的項目。
2. 假資料寫死在程式裡（id、ts、source、text、state）：
   第 1 天（now=1000）：slack S1（ts 900，有人被擋住）、S2（ts 950，閒聊）；github P1（ts 920，等你審查，open）、P2（ts 940，open）。
   第 2 天（now=2000）：slack 新增 S3（ts 1500，事故後續）；github 這天讀取失敗，回傳 {"error": "auth failed"}。
3. 讀來源照官方步驟：從「書籤減 10」開始讀；沒有書籤就讀全部。
4. 每天用 practice/llm_agent.py 的 ask_json 呼叫 claude -p 一次（共 2 次）。提示詞放入 preferences、bookmarks.json、ledger.md、各來源讀到的項目或錯誤，要求回傳 {"lines":[{"id":...,"text":...,"kind":"new|carried"}], "unreadable":[來源名], "cuts":[{"id":...,"reason":...}]}。規則照 agent.md：帳本裡狀態沒變的不重報、仍開著的最多標 carried 一行、讀不到的來源列在 unreadable 而不是當成沒事。
5. 假貼文函式回傳 {"ok": true, "ts": now}。ok 為 true 之後才記帳：每個回報項目寫一行 ledger（日期、來源、id、state）；成功讀到的來源書籤移到 now，失敗的不動；寫 runs/day1.md、runs/day2.md。
6. 第 2 天結束後用程式檢查並印 PASS／FAIL：a. 第 2 天沒有 kind 為 new 且 id 已在第 1 天 ledger 的項目；b. unreadable 含 github；c. bookmarks.json 的 github 仍是 1000、slack 是 2000；d. lines 不超過 5 行。兩天的簡報、檢查結果與模型呼叫次數寫進 ch09/interactive/brief_report.md。
```

**觀察重點**：

- 第 2 天從 990 開始讀，Slack 是否只讀到 S3？簡報有沒有把 S1、P1、P2 當新項目再報一次？
- github 失敗時，模型是否把它列進 unreadable，而不是當成沒有新動態？書籤是否仍停在 1000？
- 四項檢查是否全 PASS？（輸出可能不同，照實記錄）
